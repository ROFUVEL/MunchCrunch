# MunchCrunch

MunchCrunch — веб-приложение для оформления заказов в сети ресторанов.

Система позволяет клиентам просматривать меню, выбирать ресторан, оформлять заказы и отслеживать их статус.

## Основные возможности

### Клиент

* Авторизация по номеру телефона и коду подтверждения;
* Выбор точки обслуживания;
* Просмотр меню ресторана;
* Добавление блюд в корзину;
* Оформление заказа;
* Просмотр истории и статусов заказов;
* Просмотр профиля.

## Используемые технологии

## Установка и запуск

### 1. Клонирование репозитория

```bash
git clone https://github.com/ROFUVEL/MunchCrunch.git
cd MunchCrunch
```

### 2. Установка зависимостей

```bash
npm install
```

### 3. Настройка базы данных

Установите PostgreSQL и создайте **новую пустую БД** `munchcrunch_demo`.
Из корня проекта выполните (утилиты PostgreSQL должны быть в PATH):

```powershell
createdb -h localhost -U postgres munchcrunch_demo
psql -h localhost -U postgres -d munchcrunch_demo -v ON_ERROR_STOP=1 -f database.sql
```

Альтернатива в pgAdmin: создайте БД `munchcrunch_demo`, откройте для неё Query Tool,
загрузите `database.sql` и выполните весь файл.

Скрипт создаёт 8 таблиц без сессий и добавляет 3 пользователей, 3 ресторана,
4 категории, 12 блюд и 6 заказов с позициями. Первый пользователь имеет заказы
во всех пяти статусах. В некоторых ресторанах отдельные блюда недоступны.
Суммы заказов проверяются внутри SQL-транзакции.

Скрипт предназначен для однократного запуска в пустой БД: существующие таблицы
и данные он не удаляет. Для повторного заполнения создайте другую пустую БД.

### 4. Настройка подключения

В PowerShell задайте переменные окружения перед запуском сервера:

```powershell
$env:PGHOST = 'localhost'
$env:PGPORT = '5432'
$env:PGDATABASE = 'munchcrunch_demo'
$env:PGUSER = 'postgres'
$env:PGPASSWORD = 'ваш_пароль_PostgreSQL'
```

Их читает `backend/db.js`. Файл `.env` автоматически не загружается.

### 5. Запуск приложения

```bash
node backend/server.js
```

или

```bash
npm start
```

Если PowerShell блокирует `npm.ps1`, используйте `npm.cmd start`.

Откройте `frontend/index.html` через расширение Live Server в редакторе.
Frontend обращается к API `http://localhost:3000/api` (настройка в
`frontend/js/config.js`). Express запускает только API и не раздаёт HTML.

### 6. Проверка на тестовых данных

1. Войдите с телефоном `79999999999` без пробелов и кодом `1234`.
   Код создаётся при нажатии кнопки входа и действует 5 минут.
2. Выберите ресторан, откройте меню и добавьте блюда в корзину.
3. Оформите заказ и откройте «Мои заказы»: появится новый заказ и история
   из пяти тестовых заказов в разных статусах.
4. Для другого пользователя войдите с телефоном `78888888888` и кодом `1234`:
   у него отдельная история из одного тестового заказа.

После удаления сессий API использует переданный `userId` без проверки владельца.

## База данных

Основные таблицы системы:

* users
* branches
* categories
* dishes
* branch_dishes
* orders
* order_items
* auth_codes


Приложение содержит только клиентский интерфейс и API. Статусы заказов отображаются из базы данных;
клиент может посмотреть состав заказа и отменить заказ в статусе `created`.
Управление меню и обработка заказов сотрудниками в приложение не входят.

## Ответы API

* `200` — успешная загрузка, отправка кода, подтверждение входа или отмена заказа.
* `201` — заказ создан.
* `400` — некорректные данные запроса или недоступное блюдо.
* `401` — неверный или просроченный код подтверждения.
* `403` — заказ не принадлежит переданному пользователю (это не заменяет авторизацию).
* `404` — объект или маршрут не найден.
* `409` — заказ уже нельзя отменить из-за его статуса.
* `500` — внутренняя ошибка сервера без технических подробностей в ответе.

Ошибки имеют формат `{ "error": "Описание ошибки" }`.
Повторяющиеся `dishId` при создании заказа объединяются: их количества складываются.
Пустое меню существующего ресторана и пустая история существующего пользователя возвращают `200` и `[]`.

Состав заказа: `GET /api/users/:userId/orders/:orderId/items`.
Отмена заказа: `POST /api/users/:userId/orders/:orderId/cancel` (тело запроса не требуется).
Оба маршрута пока используют переданный `userId` без сессий и токенов.
